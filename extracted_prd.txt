1. Executive Summary
HealthAI's consumer application currently spans authentication and onboarding, AI-powered health report analysis, a medicines hub, family management, AI chat, and account settings. As HealthAI scales toward hospital, clinic, insurer, and enterprise-wellness partnerships, the platform requires a Super Admin layer that governs every tenant, user, AI model, content asset, and compliance obligation running on top of the existing consumer experience.
This document specifies a production-ready, cloud-native Super Admin platform designed as a governance and operations layer above the existing HealthAI application — not a replacement for it. It is built multi-tenant from the ground up so that hospital groups, diagnostic chains, insurers, and direct-to-consumer deployments can each operate in logically isolated workspaces while SMARTnCODE retains a single global control plane.
1.1 Objectives
Enable centralized management of unlimited tenants (hospitals, clinics, insurers, corporate wellness programs, and the direct-to-consumer instance) from one control plane.
Provide granular role-based access control so platform staff, tenant admins, support agents, compliance officers, and billing staff each see only what their role requires.
Give operational visibility and control over the AI systems that power report analysis, medicine scanning, and the AI chat assistant — including model versioning, prompt governance, quota management, and safety monitoring.
Support DPDP Act 2023 (India), HIPAA (for US-bound deployments), and GDPR (for EU tenants) compliance through audit logging, consent tracking, and data-subject request tooling.
Provide a billing and subscription engine supporting per-tenant plans, usage-based AI billing, and consumer subscription tiers.
Deliver real-time system monitoring, security operations, and analytics dashboards suitable for executive and engineering audiences alike.
1.2 Design Principles
Multi-tenant by default — every data model carries a tenant_id and every query is tenant-scoped, with a separate global/platform scope for SMARTnCODE staff.
Additive, not disruptive — the Super Admin platform is a new set of services and a new frontend; existing HealthAI mobile app flows (documented separately) are unaffected except where an admin action (suspension, feature flag, content update) intentionally changes user-facing behavior.
Least privilege by default — every permission is opt-in per role; no role receives blanket access.
Auditability first — every state-changing admin action is logged immutably before it is considered complete.
API-first — the Super Admin frontend is a consumer of the same versioned API surface that could support future partner integrations.

2.1 Tenancy Architecture Strategy
A hybrid isolation model is recommended:
Pooled multi-tenancy (shared database, tenant_id row-level security) for standard tenants — cost-efficient, fast to provision, sufficient isolation when combined with Postgres Row-Level Security (RLS) policies enforced at the database layer, not just the application layer.
Bridge model (dedicated schema per tenant) offered as a premium/regulated tier for large hospital groups or insurers with contractual data-residency requirements.
Silo model (fully dedicated database/cluster) reserved for government or extremely large enterprise deployments, mirroring the isolation pattern already proven in the Maharashtra Excise Department deployment for SmartVakheel.

4.3 RBAC Enforcement Architecture
Every API request carries a signed JWT with role, tenant_id, and a permission-scope claim issued at login and refreshed on role change.
The API Gateway performs coarse-grained route authorization; each microservice performs fine-grained, resource-level authorization against the Permissions Service.
PostgreSQL Row-Level Security policies provide a second enforcement layer so that even a compromised application token cannot read across tenant boundaries.
Permission changes take effect within 60 seconds via a short-lived permission cache with pub/sub invalidation (Redis + event bus), avoiding immediate forced re-login for most changes.

6. AI Administration Module
HealthAI's core differentiation is its AI: report analysis and scoring, medicine label scanning, drug-interaction checking, and the AI chat assistant. This module gives platform admins operational control over that AI surface.
6.1 Sub-Modules
Model & Version Registry
Track which model/version powers each AI feature (report scoring, OCR extraction, interaction checking, chat) with rollback capability.
Prompt & Policy Library
Versioned system prompts, safety instructions, and per-tenant prompt overrides (e.g., a hospital's preferred bedside-manner tone for the AI chat).
Usage Quotas & Rate Limits
Per-tenant and per-user daily/monthly caps on report scans, chat messages, and medicine scans, with overage billing hooks.
Safety & Moderation
Review queue for flagged AI chat conversations, hallucination reports on report analysis, and confidence-score thresholds that trigger human review.
Evaluation & Accuracy Reports
Ongoing precision/recall tracking for OCR extraction and interaction-risk scoring, mirroring the multi-layer validation approach used in SmartVakheel's citation pipeline.
A/B & Canary Rollouts
Stage new model versions to a percentage of tenants/users before full rollout, with automatic rollback on error-rate spikes.
7. Content Management
Medicine Database — canonical medicine records (dosage, warnings, interactions) with source attribution, versioning, and a review workflow before publishing changes live to the Medicines Hub.
Health Knowledge Base — articles and AI-assistant reference material, with tenant-level visibility overrides (e.g., an insurer promoting specific preventive-care content).
Notification Templates — transactional (OTP, report-ready, reminder) and marketing templates, versioned and localized.
Localization Management — central translation memory across the 23 supported languages, with per-string approval workflow and missing-translation detection.

16. Database Architecture
16.1 Multi-Tenancy Data Strategy
Primary operational data uses PostgreSQL with a shared-schema, row-level-security model as the default. Every tenant-scoped table includes a tenant_id column and an RLS policy of the form current_setting('app.tenant_id') = tenant_id, set per-connection by the API layer immediately after authentication.

16.3 Analytics Store
Operational Postgres data is streamed via CDC (Debezium) into a columnar analytics store (ClickHouse or BigQuery, matching whichever the rest of SMARTnCODE's stack already standardizes on) to keep heavy aggregate queries off the transactional database.
17. API Architecture
RESTful JSON API as the primary surface, versioned via URL prefix (/api/v1/...), consistent with the architecture pattern already used across SmartVakheel and SMART HCM AI.
GraphQL gateway offered as a secondary surface for the Analytics and Dashboard modules where flexible, nested queries reduce over-fetching.
All admin-facing endpoints require a valid admin JWT with tenant and role claims; service-to-service calls use mutual TLS plus short-lived service tokens.
Idempotency keys required on all state-changing endpoints used by bulk-action tooling (bulk suspend, bulk export) to make retries safe.
Standard envelope: { data, meta: { pagination, requestId }, errors[] } across every endpoint for predictable client handling.

18. Deployment Architecture
Kubernetes (EKS/AKS/GKE, matching whatever the existing HealthAI and SmartVakheel infrastructure already runs on) with each microservice as an independently scalable deployment.
Environment separation: dev → staging → production, with tenant-level canary flag to route a specific pilot tenant's traffic to a staging-equivalent "canary" production pool before full rollout.
CI/CD via GitHub Actions or GitLab CI: lint → unit tests → container build → staging deploy → automated smoke tests → manual approval gate → production deploy.
Blue-green or rolling deployment strategy per service, with automatic rollback triggered by the Monitoring Service on error-rate spikes.
Secrets managed via a dedicated secrets manager (AWS Secrets Manager / HashiCorp Vault); no credentials in environment files or source control.
Database migrations run as a separate, gated pipeline step with backward-compatible (expand/contract) migration discipline to support zero-downtime deploys.

19. Key Workflows & Sequence Flows
The following flows are expressed as ordered steps; each corresponds to a sequence diagram in the companion interactive architecture diagram set.
Tenant Onboarding
Step 1: Sales/Ops initiates provisioning via Tenant Management wizard.
Step 2: Tenant Service creates tenant_id, default plan, and namespace config.
Step 3: Identity & Access Service creates the first Tenant Admin invite (email/SMS via Notification Service).
Step 4: Tenant Admin accepts invite, completes branding and feature-flag setup.
Step 5: Billing Service activates the assigned plan; usage metering begins.
Step 6: Audit Service logs every step of the above as an immutable record.
AI Model Rollout
Step 1: Platform Admin stages a new model version in AI Admin Service (status: staged).
Step 2: Evaluation pipeline runs automated accuracy/safety checks against a held-out test set.
Step 3: Admin sets canary rollout percentage (e.g., 5% of report-analysis traffic).
Step 4: Monitoring Service tracks error rate and latency for the canary cohort.
Step 5: On success, Admin promotes to 100% rollout; on failure, automatic rollback to prior version.
Data Subject Request (DSR) Handling
Step 1: User submits an access/erasure request in the consumer app or via support.
Step 2: Request lands in the Audit & Compliance DSR workspace with an SLA countdown.
Step 3: Compliance Officer verifies identity and reviews scope of held data across services.
Step 4: System executes export or erasure across User Directory, Content, Billing, and Audit services as applicable.
Step 5: Confirmation sent to the user via Notification Service; action logged in Audit Service.
Tenant Suspension (Non-Payment)
Step 1: Billing Service flags an invoice as overdue past the grace period.
Step 2: Tenant Service transitions tenant status to Suspended.
Step 3: API Gateway begins returning read-only responses for that tenant's end-user traffic.
Step 4: Notification Service alerts the Tenant Admin and the assigned SMARTnCODE account owner.
Step 5: Reinstatement on payment automatically reverses the suspension via the same event pipeline.

23. Appendix: Glossary
Term
Definition
RLS
Row-Level Security — a PostgreSQL feature restricting which rows a query can see based on session context (e.g., tenant_id).
RBAC
Role-Based Access Control — permissions granted via named roles rather than individual users.
DSR
Data Subject Request — a user's formal request to access, correct, or erase their personal data under DPDP/GDPR/HIPAA-equivalent rules.
Canary Rollout
Releasing a change to a small percentage of traffic before full deployment, to catch regressions early.
CDC
Change Data Capture — streaming database changes into another system (e.g., an analytics warehouse) in near real time.
Silo / Bridge / Pooled Tenancy
Increasingly isolated multi-tenant data models, from fully shared (pooled) to fully dedicated (silo) infrastructure per tenant.
